4. ARCHITECTURE AND PROCESS BOUNDARIES

This is one repository with separately run service processes and a shared
Python library. The central import direction is:

    backend -> shared <- voice_runtime

backend and voice_runtime must not import each other's application packages.
Both can import shared. Shared code must not depend on either application.
They use the root environment configuration and the common env/ virtualenv.

Main processes and documented default local ports:

    Frontend/Vite          5199  npm run dev
    Platform API           9001  env/bin/python -m backend.main
    Voice worker           9002  env/bin/python -m voice_runtime.app
    MCP server             9003  env/bin/python -m backend.mcp_server.server
    Telephony gateway      9011  env/bin/python -m voice_runtime.gateway
    Ingestion worker          - env/bin/python -m backend.workers.ingestion

Ports are configurable. Root .env and shared/config.py determine actual values.
FreeSWITCH ESL is documented on port 9004; it is a call-control event socket,
not the REST API or a browser-facing web service.

The gateway runs the same FastAPI application on a separate configured port,
allowing a telephony provider to reach its webhook and media WebSocket at one
public host/port. It is distinct from the control-plane Platform API.

The API may embed ingestion by configuration; ingestion can also run as a
separate worker. Post-call analysis has its own embedded background polling
mechanism. Do not assume one deployment mode without checking configuration.

7. BOT CONFIGURATION, AUTHORING AND RELEASES

A bot is more than a system prompt. Its resolved configuration can include:
- System/greeting prompts and their versions/modes.
- Supported languages, STT/TTS/LLM providers, models and voice identity.
- Intent/entity definitions, workflow routing and business policies.
- Authorized knowledge sources and API/tool connections.
- Runtime/customer context, guardrails, channel and turn-detection settings.
- Goal policy, naturalness settings and recording-related configuration.

shared/bot_config.py resolves trusted bot configurations. Provider/model/
language/voice validity is governed by the database-backed provider catalog.
Do not hardcode arbitrary combinations into UI or runtime code.

Releases support publishing/rollback and pinned workflow revisions. A call
uses a pinned configuration snapshot for its lifetime; editing a bot does
not mutate an already-running call. Cache invalidation applies to later
resolutions, not to an active call's trusted snapshot.

Browser Studio testing can use the latest saved draft. Non-browser channels
require a published release. Workflow revision/pinning details are documented
in docs/architecture/orchestration-layering.md; some historical migration
compatibility paths fall back when a pinned snapshot is missing.

8. REALTIME VOICE CALL FLOW

Typical browser call:
1. An authenticated UI requests POST /api/v1/voice-sessions.
2. The API checks bot ownership and writes tenant/bot/session identity to Redis.
3. The browser connects to /ws/voice/{session_id} on the voice service.
4. The worker verifies the trusted session and resolves the bot snapshot.
5. The per-call Pipecat pipeline handles the conversation.
6. Transcripts, events, session metadata, usage and optional recording persist.
7. Post-call analysis is queued when enabled.

Typical audio pipeline:

    Audio input -> caller audio/noise gate -> Silero VAD -> STT
    -> transcript gate -> turn control -> ConversationBrain
    -> TTS -> audio output

ConversationBrain (voice_runtime/brain.py) coordinates deterministic controls,
semantic decisions, routing, workflows, knowledge retrieval and response
generation. Generated response tokens can stream toward TTS.

Important runtime behavior:
- STT segments are buffered into caller turns; one final segment does not
  necessarily mean the caller has finished the entire utterance.
- Endpointing supports configurable pause windows and Smart Turn behavior.
- Deepgram Flux has a provider-native end-of-turn path.
- Barge-in cancels in-flight generation/synthesis and controls queued audio.
- Caller noise, echo, unstable partial transcripts and late finals have
  dedicated handling; changes here can affect interruption and turn timing.
- Browser and telephony audio formats/sample rates differ. Preserve transport
  negotiation instead of applying a single sample rate to all channels.
- Per-call capacity, timeouts and duration limits are configurable.
- Per-turn metrics separate STT, endpointing, LLM, TTS and overall latency.

Relevant files include pipeline.py, brain.py, endpointing.py, turn_stop.py,
barge_in.py, audio_gate.py, transcript_gate.py, smart_turn.py, tts_router.py,
serializer.py, recording.py, turn_metrics.py and latency_breakdown.py under
voice_runtime/.

9. INTELLIGENCE, ROUTING AND BUSINESS WORKFLOWS

The runtime uses deterministic controls plus a bounded structured LLM decision
stage. GoalEngine produces validated ConversationDecision data, including
intent, signals, slot observations, scope and next action. It has a timeout
and a deterministic TurnRouter fallback.

Safety, hangup, transfer and other call-control handling must remain effective
around model-generated decisions. A model reply alone must not authorize an
external action or bypass verification/business gates.

LangGraph handles stateful business workflows: asking questions, capturing
slots, branching, validation, API actions, retries, readbacks and completion.
Audio stays in Pipecat. Ordinary knowledge/FAQ turns do not need LangGraph.

Primary checkpointing uses PostgreSQL. Documented fallback uses in-memory
state when persistent checkpointing is unavailable, which loses durability.

Current-call context questions such as "Who is calling?" can be answered
without advancing the workflow's pending step or consuming its retry budget.
The response should use the bot's actual context and resume the pending
question. It must not invent identity, location or private customer facts.

Response modes include authored exact delivery and grounded model responses.
For critical identifiers, amounts, facts or confirmations, preserve the
configured exact/readback contract. API request/response schemas, when
authored, can reject an HTTP-200 response that violates the business contract.

10. SHARED ENGINE VS TENANT-SPECIFIC BEHAVIOR

This is a particularly important maintenance boundary:
- Core engine: graph execution, state, retries, generic behavior and audit.
- Core router: generic routing composition and intent handling.
- Language packs: caller-language words and surface forms.
- Domain signal packs: domain meanings such as refusal or hardship.
- Named extensions: specialized semantic slots/resolvers where necessary.
- Workflow definitions/prompts: tenant script, nodes, business vocabulary,
  entity rules, readbacks, API mappings and tenant-specific outcomes.

Business behavior should normally be configured through workflow nodes/edges,
prompts, intents, entities and API connections. Setup scripts author those
records; they are not a separate runtime architecture.

Do not fix one tenant's wording by inserting its name, node ID, slot name or
language-specific regular expression into the shared engine/router.
Behavior versions protect existing workflow semantics. Broad changes need
replay evidence and may require a new opted-in behavior version.

tests/unit/test_core_purity.py checks this boundary. tests/golden/ contains
workflow/router replay coverage. For shared-orchestration changes, reproduce
locally and run core-purity plus golden checks. Do not re-record expected
results merely to make a regression disappear.

11. KNOWLEDGE, DOCUMENT INGESTION AND RAG

shared/knowledge/service.py exposes KnowledgeService, the common service used
by REST testing, voice conversations and external MCP tools. Voice calls use
this service directly; they do not make an MCP hop for internal retrieval.

Ingestion flow:
Upload -> extension/MIME/size/path/deduplication checks -> save original
-> create queued job -> parse -> chunk -> embed -> store -> verify -> ready.

Upload API: POST /api/v1/knowledge/{source_id}/documents.
Retrieval test API: POST /api/v1/knowledge/search-test.
Lifecycle includes status, retry, cancellation, reindex and soft deletion.

Parsing supports common document/spreadsheet/text formats. OCR fallback is
configuration controlled. Page/section metadata and document structure help
preserve useful retrieval context. Chunks are token-aware; structured tables
receive special handling rather than arbitrary splitting.

Hybrid retrieval combines pgvector cosine search and PostgreSQL full-text
search, with weighted fusion or optional RRF, deduplication, relevance gates,
optional reranking and a context budget. Returned sources carry document,
chunk, page/section and score information. Raw embeddings stay internal.

Embedding implementations include OpenAI and deterministic mocks for local
tests. Selected provider/model/dimension must remain compatible with stored
vectors and the actual PostgreSQL schema.

Knowledge scopes are bot, tenant and global. Authorized KB IDs pass through
KnowledgeService authorization and an additional SQL tenant filter.
Unanswerable retrieval should produce an honest fallback instead of invented
business policy. Retrieved content is reference data, not executable policy.

KMRAG parsing/retrieval ideas were ported into shared/knowledge/. KMRAG is not
a separately deployed service here. The documentation explicitly says there
is no implemented in-repository AgentAssist package/service.

12. AI PROVIDERS, LANGUAGES AND NATURAL SPEECH

The shared provider factory registers:
- STT: OpenAI/Whisper, Deepgram, AssemblyAI, Sarvam, mock.
- TTS: OpenAI, ElevenLabs, Azure, Google, Sarvam, Deepgram, mock.
- LLM: OpenAI, Anthropic, Google, mock.

Adapters are implemented in shared/providers/. Realtime/STT and streaming TTS
also have runtime-specific adapters. A registered adapter is not evidence
that its credentials, optional dependencies or voice catalog are configured.

Language behavior includes STT detection, allowed-language policy, runtime
language evidence, response language and TTS voice/engine selection. Treat
these as related but distinct settings. Indian-language and Hinglish support
is an important part of the product; actual capability varies by provider,
model, voice and the bot's configured languages.

Human speech naturalness uses platform defaults -> tenant overrides -> bot
overrides, with effective-value/source display. Features include breathing,
filler words, acknowledgements, latency cues, backchannels, delivery pacing,
voice identity and optional ambience. Breathing and spoken filler switches
are independent. Critical responses suppress inappropriate variation/cues.
Unsupported provider controls must degrade through the supported delivery
path. Streaming self-correction is intentionally disabled in the documented
current token path.

14. CONVERSATION RECORDS, MEMORY, USAGE AND GOVERNANCE

The recording subsystem collects transcript turns, routing/events, timings
and provider usage. Optional recordings and conversation playback are separate
from a generic voice-sample playback feature flag.

shared/post_call/ contains background analysis, structured extraction,
next-best-action logic and recall. A durable MySQL conversation-memory row
acts as a queued job with attempts/status/error; processing occurs after
call finalization instead of blocking audio teardown. Tenant flags govern
summary generation and use of previous-call summaries.

Post-call analysis can feed structured summaries and conversation metadata.
Previous-call context can be loaded for a new call when enabled. It must
respect tenant/customer identity and permitted disclosure boundaries.

The repository contains subscription, invoice, pricing, usage and reporting
models/routes/UI. Do not infer complete external payment processing or a
financial reconciliation system solely from the presence of a Billing page.

15. SECURITY AND TENANT ISOLATION

- JWT authentication and role/permission checks protect REST endpoints.
- Tenant identity comes from verified auth/session/number mappings, not an
  arbitrary client-supplied tenant ID. Super-admin administration has explicit
  scope rules; global KB retrieval is not automatic access to every tenant KB.
- Cross-tenant resource access is generally returned as sanitized not-found.
- Opaque issued voice session IDs are verified before a pipeline is built.
- Passwords are bcrypt-hashed. Password-policy and password-change timestamp
  checks invalidate previously issued JWTs after a password change.
- Secret values resolve server-side through the supported reference mechanism;
  do not place credentials in prompts, frontend bundles or new documentation.
- Soft delete/archive is the default. Hard deletes are blocked while
  ALLOW_HARD_DELETE=false.
- Audit logs cover sensitive administration, publishing, knowledge mutations,
  session issuance and MCP calls.
- Upload controls include MIME/extension checks, size limits, generated safe
  paths and deduplication.
- RAG has injection detection/sanitization and grounding instructions.
- PII masking and credential-safety rules exist, with class-specific scope.
- Outbound HTTP uses the project's safe HTTP/SSRF controls and configuration.

These are implemented controls, not proof of formal certification. Documented
limitations include heuristic injection detection, regex-scoped PII masking
and availability-oriented fail-open behavior for some Redis-backed replay/
rate-limit controls. Review the relevant current code for security work.

  local or live database. Historical README status is not a fresh audit.
- The implementation and generated route/schema definitions take precedence
