## 2. Issues, ordered by severity

Format: what happens · evidence · what should happen · likely layer · suggested fix · status vs 23-11.

### C1 — Unit OK / no-defect: "no one came" crashes the workflow (step budget) — **Critical, new**

- **What happens.** For `unit_ok_no_defect`, any "no contact" answer to *"kya aapko Haier ke technician
  ki taraf se koi call aaya tha ya koi visit hui thi?"* — "nahi, koi nahi aaya", "nahi, koi call nahi
  aaya", a bare "nahi", or "pata nahi…" then "nahi" — makes the bot say *"Is prakriya mein kuch gadbad
  ho gayi. Aapko hamare agent se joda ja raha hai."* The workflow ends with status `error`, no outcome.
  "Call aaya tha par visit nahi hui" still works.
- **Evidence.** STEP-01, STEP-02, STEP-04, STEP-06, SVC-03: FAIL in every repeat on local (v96) and demo
  (v84); **PASS on the 23-11 baseline (v80)**. Voice: the same crash over the phone path in VX-01 #2 on
  demo (cv_689c03755cd1: after *"nahi, ab koi problem nahi hai"* at the unit-OK contact question) and on
  local (cv_fb9ba59ce0a0). After saying "agent se joda ja raha hai" the bot simply carries on with the
  next question. (STEP-01 itself did not get its voice run before the stop.)
- **Why.** The workflow engine walks at most `max_node_steps = 30` nodes per caller turn
  (`shared/orchestration/behavior.py:48`); past that it replies with the canned `wf_error` text
  (`shared/orchestration/workflow_engine.py:2114-2117`). The 23-11 repairs inserted long chains of
  condition nodes (`n_haier_followup_n_intro_unit_ok_0…`, `n_haier_audit_n_intro_unit_ok_0…`) in front
  of each hub. Longest single-turn path from `n_intro_unit_ok`: **6 nodes in v80, 33 in v83 and v84**;
  `n_intro_unit_ok_clarify` 34; the bill-state service hubs reach 36 in the worst case.
- **Expected.** Apology (*"Main maafi chahungi…"*) → *"Kya aapko Haier ki taraf se service ki
  requirement hai?"* → Action 1 / Action 2.
- **Layer.** Workflow structure (repair chains) + engine guard. The fallback text promising an agent is
  platform code and is wrong for any bot without a transfer.
- **Fix.** Collapse each repair chain into one routing node per hub (or route by the capture variable
  directly on the hub's edges); add a pre-publish check that fails when any hub's longest single-turn
  path exceeds the budget (the static check used here is ~30 lines); if the budget must rise, do it per
  workflow definition, not globally; replace the `wf_error`/`wf_timeout` "agent se joda ja raha hai"
  text with a neutral retry line for bots that have no transfer.

### C2 — Bill flow: "will pay" / "haan bhej dijiye" at the new bill-now question → "payment kar diya" → completion — **Critical, new**

- **What happens.** Bot: *"Kya aapke paas ab bill available hai?"* Customer: *"Nahi, par main charges de
  dunga."* Bot: *"Samajh gayi, aapne payment kar diya hai. Kya aapke product ki problem ab theek ho gayi
  hai?"* → *"Ye installation ya service Haier ke technician ne ki thi?"* → *"…request completion ke liye
  aage bhej rahi hoon"* → outcome `redispatch_completion` = **"Connected – Issue Resolved by Haier
  Tech"**. Same with "haan, charges de dunga" (also after a clarify) and with the warranty objection
  *"charges kyun doon, warranty mein hai"* followed by "haan bhej dijiye".
- **Evidence.** BILL-09 (3/3 local, 3/3 demo → completion), BILL-06 (3/3 both), BILL-01 first version
  (2/2 both, text) and voice BILL-01 (local 2/2, demo 2/2: same lines over the phone path). Baseline v80
  did not have this question and passes BILL-06/BILL-09.
- **Why.** The hubs `n_haier_bill_state_now_q` and `n_haier_bill_state_now_clarify` (added by the bill-
  state repair) have **no yes/no edges** — only cloned "special" edges plus else/correction. An answer
  that the capture regex does not classify is routed by signal; `payment_intent`/`affirm` match the
  cloned "already paid" edge (edge #3), the first signal-compatible edge in order.
- **Expected.** Bill now? Yes → acknowledge → service requirement. No → *"Kya aap charges dene ke liye
  ready hain?"* (PDF). "Will pay" is consent to charges, never "already paid".
- **Layer.** Workflow (hub edges). **Fix.** Give both hubs explicit yes/no edges placed before the
  special edges; do not let `payment_intent` select the "already paid" edge anywhere; add BILL-06/09/10
  to the pre-publish run.

### C3 — Split / truncated answers: the bot acts on the fragment — **Critical** (telephony)

- **What happens.** A short pause after "haan," or "nahi," (normal speech) closes the turn. The bare
  yes/no is resolved instantly (deterministic lexicon), the bot starts the next question, and the rest of
  the sentence either becomes the answer to that *next* question or is discarded as `stale_new_reply`.
- **Evidence.**
  - Demo today, cv_64cb5c7f65c5 (v0.1.26, not a Haier product): *"Nahi, mere paas."* → bot cancels as
    "not a Haier product"; the continuation *"baad mein do din mein"* was discarded.
  - Demo voice test BILL-04 #1: *"Haan, technician aaya tha."* was split into "haan" (answer to the visit
    question) + "technician aaya tha" (taken as the answer to the bill question) → next answer *"us samay
    nahi tha, abhi bill hai mere paas"* was read as "no service needed" → **cancel_no_service**. The same
    audio passed on local (different endpointing).
  - 23-11: cv_14425a59bfbd ("nahi hui hai" about the visit taken as "no service" → Cancel WO),
    cv_0c2bc520470c and cv_7e9ff0b84ae7 (customer's "main khud contact kar lungi" / "maine request cancel
    kar di" discarded).
  - Voice VX-03 (*"Nahi, mere paas…"* 1.2 s pause *"…Haier ka hi hai, do din mein bhej do"*): on demo
    2 of 3 calls cancelled as "not a Haier product" on the bare "nahi" (yes/no lexicon fast path),
    cv_2b205a66c69c, cv_7d067b7f7dcc. The text run cancels even on the joined *"Nahi, mere paas."*
    (NHP-06, 3/3 on all three configurations), so this is wording **and** turn-taking.
  - Voice ECOM-02 #3 on local (cv_d06b3b6bb816): *"Nahi, geyser bilkul sahi hai, koi damage nahi hai"*
    arrived as *"Nahi. Geyser bil. Bilkul."* plus a held fragment *"sahi hai, koi damage nahi hai"*
    that was **discarded** (`stt_held_segment_discarded`, reason `no_continuation`) → cancelled as
    damaged (see H2).
  - Voice RTP-01 #1 on local: *"haan, payment nahi kiya tha"* → "haan. samay." + held *"payment nahi
    kiya tha"* discarded the same way.
  - Voice BILL-04: demo 1 of 3 wrong cancel (above), local 3/3 correct.
- **Expected.** Never take a terminal action (cancel/close) on a ≤2-word fragment when speech continues
  within ~1.5 s; merge the continuation and re-decide.
- **Layer.** Turn-taking/endpointing (demo telephony short-reply endpoint 0.3 s, stop 0.25 s) + the
  deterministic yes/no fast path + the stale-reply discard rule in `voice_runtime/brain.py`.
- **Fix.** Hold a bare "haan/nahi" final for ~0.6–0.8 s when VAD shows continued speech or the
  transcript ends with a comma; treat a continuation that arrives before the next reply is *heard* as
  part of the same turn (roll back, like `turn_merged_late_final`), instead of discarding it.

### C4 — Re-dispatch consent: second confirmation, then "confirm nahi ho payi" — **High, new (v83)**

- **What happens.** At *"kya technician ki visit ke liye main aapki request aage forward kar doon?"* the

  visit wali request aage forward kar doon?"* → a second yes → *"Maafi chahungi, is call par jaankari
  poori tarah confirm nahi ho payi…"* → `unverified_no_action` ("Unmapped (needs review)").
- **Evidence.** Real: demo cv_f5293164ece8 and cv_f45eb3020c04 (v0.1.25, "haan, badha dijiye" twice →
  unverified + *"Haier customer care par call karke status check kar sakte hain"*); local cv_c485f6c330a8,
  cv_d566bd0fe726. Tests on v84/v96: **CB-02** (English: *"Yes, please send the technician again"* +
  *"Yes, go ahead"* → unverified, 3/3 both envs; baseline PASS; **voice**: demo 2 of 3 unverified
  (cv_ad4dc5d5b266, cv_704b23df0b05), local 1 unverified + 1 asking the same consent question again after
  "Yes, go ahead" (cv_2589878ba9f1, cv_52744ce17285); the English intro itself was spoken correctly
  with "Refrigerator" and "complaint"), **UOK-05** (English, second confirmation),
  **UOK-06** ("haan send kar dijiye" → second confirmation), **RTP-04** (warranty hub already asked
  *"kya main re-dispatch kar doon?"*, then `n_redispatch` asks again). Fixed: "haan badha dijiye",
  "haan kar dijiye", "haan bhej dijiye" (UOK-03, CNS-04 pass both envs).
- **Expected.** One confirmation; any clear affirmative (Hindi/English/Hinglish) accepted; never close as
  unverified after two affirmatives.
- **Layer.** Workflow capture rules on `n_redispatch` / `n_haier_audit_redispatch_confirm` (regex lists).
  **Fix.** Accept the decision model's `affirm` with no negation as consent; add English forms; make the
  second confirmation accept a bare "haan/yes"; skip `n_redispatch` when the warranty hub already got
  consent.

### C5 — 5-day rule and timing answers — **High, still**

- **What happens.** Timing hubs (`n_v2_future_when`, `_clarify`) only know vague phrases. "29 tarikh ko"
  → *"agle kuch dinon mein ya uske baad?"* → "agle kuch dinon mein, 29 tarikh ko" → **unverified close**.
  "Next Sunday / ek week ke baad" → the same question again, then unverified. "Abhi time lagega" →
  immediately *"request aage forward kar doon?"*; "ek mahine baad" is then ignored. A date given earlier
  ("next Sunday", "do din mein") is asked for again.
- **Evidence.** BILL-08 (3/3 both envs; = real local call cv_4ba9fd3f1f28 on v0.1.34, which has today's
  workflow content), ND-06, ND-07 (3/3 both); real 23-11: cv_aab4cbded4c1, cv_5588f8684a31 (re-dispatched
  on "abhi time lagega"), cv_e56b03deeb8b. Works: "do hafte baad" → cancel_service_later (RV-05),
  "Tuesday" → re-dispatch (RV-06).
- **Expected (PDF Part 4).** Within 5 days of registration → Action 1; later → softly deny, cancel, ask
  the customer to raise a new WO when needed.
- **Layer.** Workflow (no date handling) + **payload** (the request registration date is not sent, so the
  rule cannot be computed as written). **Fix.** Send `registration_date` from the dialer; capture
  dates/weekdays/"N din/hafte/mahine baad" deterministically; ask once for a date if missing; never end
  unverified when a date was given.

### C6 — "Call later" at the intro skips the reason probe — **High, still**

- **What happens.** Callback words at the first question ("baad mein jo bhi chahiye", "abhi aapko call

  hoon, aap installation ya visit ke liye lagbhag kab available honge?"* — the Haier-product / delivery /
  bill / payment probe is never asked, complaints are asked about "installation", and a date leads to

- **Evidence.** NHP-05: not-a-Haier-product request **re-dispatched** after "abhi aapko call karunga" +
  "parson" (3/3 both); BILL-08 (as C5); real: demo cv_f45eb3020c04 (v0.1.25), local cv_4ba9fd3f1f28
  (v0.1.34), 23-11 cv_729685adcb89, cv_e56b03deeb8b.
- **Expected.** Treat as "busy / call me later" (see C10) or, if the customer is talking about timing,
  keep the reason probe first.
- **Layer.** Workflow (special edges on every intro hub). **Fix.** Route callback/busy on intro hubs to a
  busy branch; keep scheduling only after the reason probe and service requirement.

### C7 — Completed installation read as "part pending" — **High, new (v84)**

- **What happens.** v84 changed the completion question to *"Kya is product ki installation ya service
  ka koi kaam abhi baaki hai?"* The natural answer *"Haan sab ho gaya, … koi dikkat nahi hai"* starts with
  "haan" (= "yes, work is pending" literally) → *"Samajh gayi, repair, replacement ya part abhi pending
  hai. Kya iske liye pehle se koi request open hai?"* → closed as `existing_case_followup` with *"is call
  se nayi request nahi banayi ja rahi hai"*.
- **Evidence.** ND-05 (2/3 → existing case, 1/3 loop; both envs). Baseline v80 → correct completion
  (3/3).
- **Fix.** Ask positively (*"kya installation poora ho gaya hai?"*) or let "sab ho gaya / koi dikkat nahi"
  override a leading "haan"; never infer "part pending" without part/replacement words.
